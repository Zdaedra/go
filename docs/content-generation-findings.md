# Генерация задач: метод, результаты, находки

**Дата:** 2026-07-11 · **Код:** `scripts/gen_tsumego.py`, `scripts/merge_generated.py`, `scripts/cross_check_katago.py`

Цель: 1000+ задач, равномерно по 6 навыкам, чистая лицензия, включая лёгкий
низ (850–1500) для истинных новичков — без транскрипта копирайтных книг.

## Метод

**Композиция + сертификация решателем.** Канонические public-domain формы ×
8 симметрий × трансляции → задачи-кандидаты. Собственный решатель сертифицирует
каждую: (1) уникальный ключевой ход, (2) дерево (верная линия + опровержения),
(3) оценка сложности. **Домен известен по построению** — это обходит
провалившийся ownership-классификатор Р1b: «capture»-шаблон физически не может
дать не-capture задачу.

## Что сделано и доказано

### capture — ✅ готово, влито
- Решатель захвата (attacker/defender negamax) сперва **провалидирован на 5
  seed-задачах с известными ответами** (воспроизвёл ключи с уникальностью).
- 876 сертифицированных → **196** субсэмпл, сложность **850–1050** (новичковый
  низ, которого не хватало).
- **Двойная верификация:** все 196 → `solved` через настоящий движок
  приложения; в 10/10 расхождениях с KataGo ключ решателя реально снимает
  1–3 камня.
- Влито: домен capture 47 → 243, всего задач 1039 → 1235. Аудит дерева чист.

### KataGo кросс-чек — ✅ выполнен, дал важную находку
Прогон 40 capture-задач через KataGo (Vast GPU): **24/40 совпало (60%)**.
Разбор всех 16 расхождений: **ключ решателя захватывает во всех, ход KataGo — ни
в одном.**

> **Находка: KataGo — неправильный оракул для тривиального захвата.** KataGo
> максимизирует счёт (площадь) по всей доске; снять один камень на почти пустой
> 9×9 дешевле, чем занять центр, поэтому KataGo играет большой пункт, а не
> захват. 60% «совпадения» — лишь там, где захват и есть крупнейший ход.
> Решатель отвечает на точный вопрос («форсировать захват») и потому корректнее
> KataGo для этого класса. Ключи дважды доказаны (движок приложения + ручная
> проверка захвата).

Технические заметки по Vast-пайплайну (для повторного запуска):
- KataGo — AppImage; FUSE нет → распакованный бинарь
  `/root/katago/squashfs-root/usr/bin/katago` + `LD_LIBRARY_PATH=.../usr/lib`.
- Интерактивный Popen умирает после 1 запроса → **батч-режим** (все запросы в
  stdin, `communicate`, читаем все ответы).
- Локальность: не `allowMoves` (только depth 1), а **`avoidMoves` вне региона,
  untilDepth 50, оба игрока** — и **тесный регион** (1 кольцо либертей), иначе
  KataGo уходит на большой пункт.

### Прорыв (2026-07-11): КРОП на под-доску чинит оракул KataGo

Проблема KataGo (максимизация площади → tenuki в центр) решается **кропом
задачи на её собственную маленькую доску**: bounding box формы + тонкий отступ,
края кропа = стены. На тесной доске нет большой пустой зоны, и захват/убийство
группы становится крупнейшим ходом — KataGo решает локально. Замер (crop margin
в `cross_check_katago.py`, по умолчанию crop; `--no-crop` = старый режим):

| Режим | capture (40) | kill/ld (4) |
|---|---|---|
| вся доска, best-move | 0% (центр) | 0/4 |
| crop margin 1 | 85% | — |
| **crop margin 2** | **92.5%** | **3/4** |

Остаточные промахи: угловые захваты с альтернативным пунктом + «pass»-артефакт
(не ошибки решателя — он доказан движком 196/196); side3 — широкая форма, даже в
кропе большая (там надёжнее ownership). **Вывод: crop + KataGo — рабочий оракул
для ld/race/connect.** Для компактных форм хватает best-move; для широких —
ownership. Best-move остаётся неверным на ПОЛНОЙ доске (ниже).

### Ранее: «лучший ход» KataGo не годится на ПОЛНОЙ доске

Прогон 4 окружённых seed KILL-форм с известной витальной точкой: **0/4** — KataGo
снова играет в центр (D7/E6/D6/F6). Причина: если группа уже мертва, KataGo не
спешит занимать витальную точку (убьёт когда угодно) и берёт крупнейший пункт по
площади. То есть `moveInfos[0].move` — **неправильный запрос для ld** (как и для
capture). Правильный оракул — **ownership**: сыграть кандидата, запросить
`includeOwnership:true`, проверить, что очки целевой группы уверенно у атакующего
(мертва) при витальном ходе и у защитника (жива) при остальных. Витальная точка =
единственный ход, флипающий ownership. Это следующая итерация тулинга
(`cross_check_katago.py` возвращает лучший ход; нужен вариант со статусом).
`data/tsumego/domains_cache.jsonl` уже содержит ownership (own_a/own_b) — сигнал есть.

**Почему CPU-решатель «двух глаз» отложен (EXPERIMENTAL).** Захватываемость
как модель жизни корректна только для **полностью окружённых** групп. Seed
LIVE-формы — голые угловые/боковые формы глаза с выходом на открытую доску, для
них захватываемость не определена → `ld_self_test` не воспроизводит ключи (падает
by design, документирует ограничение). Для ld генерируем **окружённые** формы и
верифицируем статус через KataGo (правильный вопрос — «жива ли группа после
хода», а не «лучший ход по площади»).
