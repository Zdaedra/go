## 1. Контекст и текущее состояние (as-built)

Приложение: React Native + Expo, iOS. Вкладка «Обучение» — тренажёр цумэго
в стиле lichess puzzles. База: **1039 задач** (сид-наборы + Gokyo Shumyo 508,
Xuanxuan Qijing 343, Igo Hatsuyoron 174), у 1038 есть верифицированные KataGo
деревья решений (`tree`: корректные линии + помеченные ошибочные ходы с
опровержениями). Все задачи офлайн, движка на устройстве нет.

### 1.1 Что уже работает

- **Elo по доменам**: 6 доменов (capture / ld-live / ld-kill / ko / race /
  connect). Старт 1100, K=48 первые 10 попыток в домене, дальше K=24.
  `P(solve) = 1/(1+10^((D−R)/400))`.
- **Подбор задачи** (`pickNext`): (1) просроченные повторы провалов;
  (2) совместный выбор (домен, задача): минимизируется
  `|P(solve) − target| + (R_domain − R_min)·0.0004`, target = 0.85 первые
  8 попыток (разогрев), затем 0.75. Домен не повторяется более 2 раз подряд.
- **Интервальные повторы**: провал → вернётся через 4 задачи; решена с
  повтора → через 12; решена с первой → через 60.
- **Очки**: `ceil(difficulty/100)`, ×2 за решение с первой попытки без
  подсказки.
- **Скип**: засчитывается как провал, задача уходит в очередь повторов.
- **Неверный ход**: камень ставится (визуальная обратная связь), через
  900 мс снимается; попытка продолжается. Помеченные в дереве ошибочные
  ходы разыгрывают опровержение → статус `refuted` (= провал).

### 1.2 Текущая шкала сложности (проблема)

Сложность — **статический прайор** 800..2500, назначенный один раз скриптом
`annotate_tsumego_difficulty.py`:

```
difficulty = BASE(сборник) + TWEAK(раздел) + (depth−1)·60 + max(0, stones−8)·8
BASE: capture 850, life-death(seed) 1050, gokyo 1500, xuanxuan 1750, hatsuyoron 2100
clamp [800, 2500]
```

Фактическое распределение: 14 задач < 1500; горб 1600–2000 (750 задач);
хвост 2200–2600. **Дыра 900–1500** — новичку строить лестницу не из чего.
Рейтинг задачи от реальных результатов пользователя не уточняется.

### 1.3 Прочие известные дефекты

- Подсказка одноуровневая: текст `problem.hint`; точка `hintMove()`
  вычисляется, но призрачный камень НЕ отображается (баг UI).
- Оценка попытки бинарная: решение со 2-й/3-й попытки, с подсказкой и без —
  для Elo неразличимы (подсказка лишь снимает ×2 к очкам).
- Нет пути «не могу вообще»: показать решение нельзя, только скип.
- Нет защиты от фрустрации (серия провалов ничего не меняет).
- Время решения не учитывается и не логируется.

## 2. Цели v2

1. **Градуированная оценка попытки** — 2-я/3-я попытка и подсказки должны
   ослаблять результат, а не обнулять/игнорироваться.
2. **Многоуровневые подсказки** — от темы к области и к точному ходу,
   с растущей ценой.
3. **Путь капитуляции** — «Показать решение» с проигрыванием главной линии
   и мягким планированием повтора.
4. **Честная шкала сложности** — динамический рейтинг задач + пересчёт
   прайоров + заполнение дыры 900–1500 лёгкими задачами.
5. **Антифрустрация** — реакция на серии провалов, стабильный поток
   «поток/успех» (target success band).

Не-цели v2: мультиплеер, серверная синхронизация рейтингов между
пользователями, генерация задач движком на устройстве.

## 3. Функциональные требования

### 3.1 Градуированная оценка попытки (score model)

Каждая попытка завершается score ∈ [0,1], который идёт в Elo-апдейт вместо
бинарного 0/1 (`delta = K·(score − expected)`).

| Исход | score |
|---|---|
| Решена с 1-го хода, без подсказок | 1.0 |
| Решена, 1 ошибочный ход ИЛИ подсказка ур.1 | 0.8 |
| Решена, 2 ошибочных хода ИЛИ подсказка ур.2 | 0.6 |
| Решена, 3+ ошибок ИЛИ подсказка ур.3 (показан ход) | 0.4 |
| Решена после «Показать решение» (повтор своими руками) | 0.2 |
| Refuted / скип / капитуляция без повтора | 0.0 |

Правила комбинирования: берётся **минимум** по всем штрафующим событиям
(не произведение — чтобы серия мелких штрафов не обнуляла решение).
Ошибочный ход = снятый камень (off-tree) или разыгранное опровержение,
если после него дана вторая попытка (см. 3.4).

Очки (points): `ceil(difficulty/100) · score`, минимум 1 при score > 0.
Отображение пользователю: «Решено со 2-й попытки: +N очков, рейтинг +Δ».

### 3.2 Многоуровневые подсказки

Кнопка «Подсказка» даёт до 3 уровней, каждый следующий — по повторному
нажатию. Состояние уровня хранится в сессии задачи.

- **Ур.1 — Тема** (score cap 0.8): текстовая формулировка, ЧТО делать и
  ГДЕ примерно: «Белая группа в углу может умереть — найди витальную
  точку». Генерация: из `domain` + `problem.hint` (уже есть) + автотекст.
- **Ур.2 — Область** (score cap 0.6): на доске подсвечивается регион —
  bounding box всех ходов корректных линий дерева, расширенный на 1
  пункт (полупрозрачная подсветка пунктов). Считается из `tree` на лету,
  разметки не требует.
- **Ур.3 — Ход** (score cap 0.4): призрачный камень на точке первого
  корректного хода (`hintMove()` — починить существующий баг: точка
  вычисляется, но не рисуется).

После ур.3, если пользователь ставит подсказанный ход, задача продолжается
как обычно (в длинных задачах подсказка сбрасывается для следующего хода —
уровни считаются заново, но score cap остаётся минимальным достигнутым).

### 3.3 «Не могу вообще»: Показать решение

Кнопка «Показать решение» доступна после ≥1 ошибки или ≥1 подсказки
(чтобы не поощрять мгновенную капитуляцию), а также всегда после refuted.

Поведение:
1. Анимированное проигрывание главной корректной линии (ходы обеих сторон,
   темп ~700 мс/ход, со звуком камней), затем подпись-объяснение
   (`problem.hint` + название темы).
2. Предложение «Повтори сам»: доска сбрасывается, пользователь обязан
   воспроизвести линию. Успех → score 0.2 («решена после показа»).
   Отказ/ошибка → score 0.0.
3. Задача планируется на повтор через 4 позиции (как провал) — при
   повторе решение уже не показывается автоматически.

### 3.4 Ошибочные ходы и повторные попытки

- Off-tree ход: камень ставится, флэш 900 мс, снимается (как сейчас),
  счётчик ошибок +1, попытка продолжается. Максимум ошибок на попытку — 5,
  дальше принудительно предлагается «Показать решение».
- Помеченный ошибочный ход (есть опровержение): опровержение
  разыгрывается, показывается «Это не работает: …», затем — НЕ провал
  сразу, а **вторая попытка** той же задачи с чистой доски (счётчик
  ошибок +1, score cap согласно таблице). Refuted = провал только после
  2-го опровержения в одной задаче.

### 3.5 Динамический рейтинг задач (двухслойная сложность)

- `difficulty_prior` — как сейчас (статический, из скрипта).
- `difficulty_live` — уточняется после каждой попытки любого пользователя
  устройства: Elo-апдейт задачи как «соперника»: `D += K_p·(expected −
  score)`, K_p = 32 первые 5 попыток по задаче, дальше 16. Хранится в
  профиле (AsyncStorage), при сбросе профиля возвращается к prior.
- В подборе и расчётах используется `difficulty_live ?? difficulty_prior`.
- Ограничение дрейфа: |live − prior| ≤ 400 (одиночный пользователь —
  данных мало, prior остаётся якорем).

### 3.6 Пересчёт прайоров (офлайн, скриптом)

Улучшить `annotate_tsumego_difficulty.py`, добавив сигналы, которые уже
можно получить бесплатно из имеющейся разметки KataGo:

- **Очевидность первого хода**: policy-вероятность корректного первого
  хода из KataGo (у нас сохранены `moveInfos` в чекпоинтах разметки).
  Низкий policy при верности хода = неочевидная витальная точка → +сложность.
- **Число корректных первых ходов**: 1 единственный ход труднее, чем 3
  равноценных.
- **Ветвистость опровержений**: больше помеченных ловушек → выше сложность.
- Перекалибровать так, чтобы монотонность сохранялась внутри сборника
  (Gokyo проще Xuanxuan в среднем), но соседние сборники перекрывались.

### 3.7 Заполнение дыры 900–1500 (контент)

Сгенерировать программно + верифицировать KataGo **150–250 элементарных
задач**: атари (1 ход), лестницы 2–4 хода, сети (гэта), связки/разрезания,
«жизнь: сделай два глаза из готовой формы», «убей: заполни витальную
точку», простые семиай 2–3 либерти. Генератор — скрипт по шаблонам форм со
случайными смещениями/отражениями; каждую задачу прогонять через KataGo
(та же схема, что `mark_tsumego_katago.py`) и через replay-верификацию.
Целевое распределение после дозаливки: не менее 60 задач в каждой полосе
по 100 пунктов рейтинга от 850 до 1600, по всем 6 доменам (минимум 15 на
домен в полосе 850–1300).

### 3.8 Антифрустрация и структура сессии

- **Серия провалов**: 2 провала подряд → следующая задача выбирается с
  target 0.9 (успокоительная); 3 подряд → 0.95 и показ подбадривающего
  текста. Серия сбрасывается любым решением.
- **Серия успехов**: 5 первых попыток подряд → target временно 0.65
  (челлендж), с явной подписью «Задача со звёздочкой».
- **Скип**: остаётся, но score 0.0 и мягкий возврат через 8 задач (не 4) —
  скип «не понял условие» не должен наказываться как провал чтения.
- Лимит подряд одинаковых доменов — 2 (как сейчас).

### 3.9 Телеметрия (локально)

Логировать в профиль по каждой попытке: id, домен, difficulty на момент
попытки, score, число ошибок, максимальный уровень подсказки, показ
решения, время до первого хода и полное время, timestamp. Ротация: хранить
последние 2000 записей. Использование: дашборд прогресса, отладка
калибровки, будущий экспорт.

Время решения в score v2 НЕ входит (спорно, вынесено в открытые вопросы).

## 4. UI-требования

1. Кнопка «Подсказка» показывает точки уровня: «Подсказка · 1/3».
2. Подсветка области (ур.2): полупрозрачная заливка пунктов региона
   в фирменном фиолетовом (#8B7CF6, alpha ~0.25).
3. Призрачный камень (ур.3): контурный камень цвета хода, пульсация.
4. Кнопка «Показать решение» появляется по правилам 3.3, стиль вторичный.
5. Счётчик попыток/ошибок в статус-строке: «Ошибка 1 из 5 — попробуй ещё».
6. Итоговый тост: score-исход словами («Решено со 2-й попытки») + очки +
   дельта рейтинга домена.
7. Повтор после «Показать решение» помечается бейджем «Повтори сам».

## 5. Данные и совместимость

- Формат профиля дополняется полями: `problems[id].liveDifficulty`,
  `attemptLog[]`, `failStreak`, `winStreak`. Миграция: отсутствующие поля
  инициализируются дефолтами, старые профили работают без сброса.
- `tsumego.json` НЕ меняет формат для 3.1–3.5 (регион подсказки и главная
  линия выводятся из `tree` на лету). Для 3.6–3.7 — офлайн-регенерация
  файла тем же пайплайном (extract → mark → annotate).

## 6. Приёмочные критерии

1. Юнит-тесты движка: таблица score-исходов (3.1), капы подсказок,
   лимит ошибок, вторая попытка после опровержения, дрейф live-рейтинга
   и его ограничение, антифрустрационные target-переключения.
2. Симуляция холодного старта (скрипт): виртуальный пользователь силы
   1000/1400/1800 — доля успешных первых 20 задач в полосе 60–90%,
   отсутствие задач с P(solve) < 0.3 в первых 10 подачах.
3. Симуляция сходимости: live-рейтинг задачи с искажённым prior (±300)
   сходится к истинному за ≤ 25 попыток.
4. UI-проверка на устройстве: все 3 уровня подсказки видимы, показ
   решения проигрывается, счётчики корректны.
5. Все новые сгенерированные задачи проходят replay-верификацию и
   KataGo-проверку решения (100%, без исключений).

## 7. Открытые вопросы (на консилиум)

1. Нужно ли учитывать время решения в score (chess.com учитывает,
   lichess нет)? Риск: наказывает вдумчивое чтение.
2. Score-таблица 3.1: линейка 1.0/0.8/0.6/0.4/0.2 — не слишком ли мягкая
   к подсказке ур.3 (фактически подарен ход)?
3. Вторая попытка после опровержения (3.4): не научит ли «тыкать» —
   может, давать её только при P(solve) < 0.5 (задача заведомо трудная)?
4. Динамический рейтинг задач на одном пользователе: имеет ли смысл, или
   ограничиться пересчётом прайоров (3.6) до появления серверной агрегации?
5. Целевой target 0.75: для гошных задач-чтения, может, правильнее 0.7
   (глубокое чтение реже награждается угадыванием, чем в шахматах)?
6. Генерация лёгких задач (3.7): шаблоны+KataGo достаточно, или брать
   готовый открытый корпус (например, задачи из открытых SGF-коллекций)?
