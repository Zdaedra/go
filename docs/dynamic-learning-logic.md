# Логика динамического обучения (KAI / go-app) — текущее состояние

**Дата:** 2026-07-11 · **Код:** `apps/mobile/src/engine/adaptive2.js`, `state/trainingStats.ts` · **База ТЗ:** adaptive-tz v3.3

Документ описывает: (1) как система учитывает каждую **пройденную пользователем задачу**, (2) общую логику подбора и роста, (3) **структуру базы задач**. Это «как оно работает сейчас», не план.

---

## 0. Ключевая идея: два контура, один рычаг сложности

| | Контур 1 «Диагностика» | Контур 2 «Обучение» |
|---|---|---|
| Что отвечает | насколько силён игрок (Auser, Elo) | что подсказать, когда повторить, какая тема слабее |
| Сигнал | `Q_rating ∈ {0,1}` — чистая первая встреча | `Q_learning ∈ [0,1]` — качество попытки |
| Когда обновляется | **только первая встреча** с задачей | **каждый** эпизод |
| Куда идёт | рейтинг → подбор сложности | очки, мастерство домена, очередь повторов |

Оба контура питаются **из одного и того же события** — завершённого эпизода. Один рычаг сложности (`Dtarget`) выводится из рейтинга. Никаких отдельных «уровней сложности» — только целевая вероятность решения.

## 1. Как учитывается КАЖДАЯ пройденная задача

На каждую задачу в профиле хранится запись `rec` (в `profile.problems[id]`):

```js
{
  firstMeetingDone: bool,   // была ли первая встреча (для rated-обновления)
  tries: int,               // сколько раз задача подавалась
  solved: bool,             // решена ли когда-либо самостоятельно
  hintRungMax: 0..4|null,   // самая глубокая раскрытая ступень подсказки
  seenSolution: bool,       // смотрел ли разбор («показать решение»)
  qRating: 0|1|null,        // результат первой встречи (для аудита)
  source: 'trainer'|'catalog'|'placement', // откуда пришла первая встреча (Д11)
  dueEpisode: int|null,     // на каком счётчике эпизодов задача вернётся
  wasDueWhenServed: bool,   // подавалась ли как «повтор по сроку» (для очков)
}
```

**Что происходит при завершении эпизода** (`recordEpisode(profile, problem, outcome)`):

1. **Определяется, первая ли это встреча** (`isFirst = !rec.firstMeetingDone`).
2. **Считаются два Q:**
   - `Q_learning` = `min(база_по_ошибкам, потолок_подсказки, потолок_H0)`.
     База: 0 взвеш. ошибок → 1.0 · ≤1 → 0.65 · ≤2 → 0.35 · >2 → 0.10. Показ решения / не решил → 0.
     Потолок подсказки: H0 1.0 · H1 0.55 · H2 0.35 · H3 0.15 · H4 0.0.
   - `Q_rating` = 1 **тогда и только тогда**, когда: первая встреча ∧ решил сам ∧ 0 взвешенных ошибок ∧ не глубже ручного H0. Иначе 0. (Не первая встреча → эпизод не rated, `Q_rating=null`.)
3. **Контур 1 (рейтинг), только первая встреча:**
   `E = 1 / (1 + 10^((D − Auser)/400))` — ожидаемая вероятность решить.
   `ΔAuser = K · (Q_rating − E)`, где `K=40` до 30 rated-эпизодов, дальше `K=20`.
   Auser растёт при решении задач сложнее рейтинга, падает при зевках на лёгких.
4. **Контур 2 (обучение), каждый эпизод:**
   - `tries += 1`, обновляются `solved / seenSolution / hintRungMax`.
   - **Мастерство домена** (EWMA): `M_s = 0.3·Q_learning + 0.7·M_s` (старт 0.6). Только аналитика — в рейтинг не входит.
   - **Frustration transient** (единственная динамика поверх Auser): 2 из 3 последних `Q_learning ≤ 0.15` → `+0.06` к целевой лёгкости; 4 из 5 `≥ 0.9` → `−0.04`; иначе затухание к 0.
5. **Очередь повторов** (`dueEpisode`):
   - не решил / смотрел решение → вернуть через **5** эпизодов;
   - решил, но не с первой попытки / с ошибками → через **12**;
   - чистое решение с первого раза → внутрисессионно не повторяем (`dueEpisode=null`), но межсессионный SRS ставит `dueDate` по интервальной лестнице (см. §7 фаза 2).
6. **Очки** (анти-фарм, отдельная сущность от рейтинга):
   `base = ceil(D/100)`.
   - первая встреча: `round(base · Q_learning)`, `×2` если `Q_rating=1`;
   - повтор **в срок** (`wasDueWhenServed`): `round(base · Q_learning)`, без `×2`;
   - повтор **вне срока**: `0` (нельзя фармить);
   - `+round(0.2·base)` за воспроизведение решения после разбора.

**Итог:** одна пройденная задача → обновляет рейтинг (если первая встреча), мастерство своего домена, frustration-окно, ставит себя в очередь повторов и начисляет очки. `solved/failed` инкрементятся для статистики точности.

## 2. Контур 1: рейтинг и старт «с самого низа»

- `ability = Auser` (единый рейтинг; доменных оффсетов в v1 нет — поле живёт для фазы 2).
- **Старт (v3):** новый игрок = `Auser = scaleMeta.min = 1050` → уровень **«новичок»**. Никакой placement-калибровки: рейтинг поднимается обычным Elo по мере решений. Продуктовое решение — не презюмировать силу, вести человека снизу в самый верх. (Профили v2 с серединой шкалы и калибровкой не мигрируются — ключ хранилища `training.v3`.)
- **Шкала уровней** (`levelLabel`): <1250 новичок · <1400 начинающий · <1550 уверенный · <1750 сильный · <1950 очень сильный · иначе мастер.
- Пример климба: 15 чистых решений поднимают 1050 → ~1330 (новичок → начинающий).

## 3. Подбор следующей задачи

`pickNext(profile, pool, domainFilter?)`. Порядок:

1. **Фильтр темы (новое).** Если игрок выбрал область на радаре/в карточке прогресса — пул сужается до этого домена. Всё дальнейшее работает внутри темы. Запись в профиль — общая (донатит в ту же систему).
2. **Гейт повторов.** До **3** повторов за сессию, не два подряд: если есть задача с `dueEpisode ≤ counter` — подаём её (помечаем `wasDueWhenServed`).
3. **Utility по невиданным.** Целевая сложность:
   `Ptarget = clamp(0.66, 0.80, 0.72 + frustration)`,
   `Dtarget = Auser + 400·log10((1−Ptarget)/Ptarget)`.
   Для каждой невиданной задачи:
   ```
   difficultyMatch = exp(−(D − Dtarget)² / (2·120²))
   skillNeed       = 1 − M_س(домен)          // слабый домен важнее
   novelty         = 1 − (домен в последних 5)/5
   sessionBalance  = 1 − доля домена в сессии
   repetitionPenalty = 0.3 если 2 последних были тем же доменом
   utility = 0.45·difficultyMatch + 0.30·skillNeed
           + 0.15·novelty + 0.10·sessionBalance − repetitionPenalty
   ```
   Подаётся задача с максимальной utility. `σ=120` не тюнится (Д7 ТЗ).

**Скучно** → двигаем только `Ptarget` вниз (через frustration), новых рычагов не вводим.

## 4. Интерактивный выбор темы (новое)

Экран «Обучение» — не только автотраектория:
- **«Играть»** → полная адаптивная сессия (все домены, `pickNext` без фильтра).
- **Тап по узлу радара** (Захват / Жизнь / Убийство / Ко / Гонка / Соединение) → сессия только этого домена под уровень игрока.
- **Тап по карточке прогресса** внизу → то же.

Тематическая сессия **не отдельный контур**: те же лестница подсказок, лог тапов, Q, обновление рейтинга/мастерства, очки, повторы. Игрок может идти по авто-траектории или сам выбирать слабую тему — и то, и то кормит модель.

### 4b. Каталог как источник эпизодов (Д11/Д12)

Каталог (Обучение → Каталог → раздел → задача) открывает **тот же экран эпизода**, что тренажёр, а не отдельный «просмотр с текстовой подсказкой». Каждый эпизод несёт `source: 'trainer' | 'catalog' | 'placement'`.

- **Единая логика.** Лестница H0–H4, лог тапов с весами, Q_learning/Q_rating, M_s домена, dueEpisode, очки — считаются одинаково для любого `source`.
- **Rated первая встреча.** Каталожная первая встреча с задачей идёт в Elo так же, как тренажёрная (формула E сама штрафует выбор заведомо лёгких задач — фарм рейтинга невозможен). Исключение: пока placement не завершён, каталожные эпизоды Elo не трогают (не ломаем bisection), но помечают задачу виденной и пишут M_s. В v3 (старт снизу) placement выключен, поэтому каталожная первая встреча всегда rated.
- **Гейт повторов** (≤1 подряд, ≤3/сессию) — правило подбора тренажёра, к каталогу не применяется: игрок выбрал задачу сам. Но повторный каталожный эпизод — «повтор» (без ×2, очки по §6: в срок засчитываются, вне срока 0).
- **Подбор тренажёра видит каталог.** Виденная в каталоге задача теряет novelty, её домен обновил M_s (skillNeed видит реальный уровень), а её dueEpisode попадает в очередь повторов тренажёра.
- **Телеметрия.** `profile.sourceStats[source] = {episodes, cleanFirst}` — cleanSolveRate с разбивкой trainer/catalog.

## 5. Структура базы задач

Файлы: `apps/mobile/src/data/tsumego.json` (клиент) ↔ `data/tsumego/problems.json` (источник). Одна задача:

```jsonc
{
  "id": "gokyo-living-001",     // уникальный; префикс = коллекция
  "category": "gokyo-shumyo",   // коллекция: gokyo-shumyo | xuanxuan-qijing |
                                //   igo-hatsuyoron | capture | life-death
  "section": "living",          // подраздел внутри коллекции
  "title": "…",                 // отображается в каталоге (ru; вне ru — номера)
  "board": "…19×19/9×9…",       // стартовая позиция, row-major '.'/'b'/'w'
  "size": 19,                   // 9 или 19
  "to_move": "b",               // чей ход (решатель)
  "view": {c0,r0,c1,r1},        // окно доски для показа (19×19 — угол)
  "difficulty": 1174,           // Elo-сложность (шкала v2, перецентрована Р5)
  "domain": "ld-live",          // навык: capture | ld-live | ld-kill | ko |
                                //   race | connect  (см. §6 — верификация)
  "domain_legacy": "…",         // прежнее значение, если Р1 перезаписал (сейчас нет)
  "tree": [                     // дерево решения (KataGo-размечено)
    { "at": "pd", "by": "b",    //   ход (SGF-коорд), цвет
      "tag": null|"wrong",      //   "wrong" = ошибочная ветка (decoy)
      "children": [ … ] }
  ],
  "structuralTargets": [ … ],   // Р3: ключевые пункты для подсказки H1
  "h1Zone": {c0,r0,c1,r1},      // зона подсветки H1
  "marked_by": {                // Р2: провенанс разметки

}
```

## 6. Домены: что верифицировано (важное ограничение)

- **Ground-truth домены — только gokyo + seed (522 задачи):** их `domain` выведен из секций коллекции (living→ld-live, killing→ld-kill, ko, capturing-race→race, connecting→connect, oiotoshi→capture).
- **517 задач (xuanxuan 343 + hatsuyoron 174) — дефолт `ld-live`:** их секции — номера страниц, типа нет. Классификатор доменов по KataGo-ownership **не достиг гейта ≥85%** (домен — педагогическая категория, эвристикой из позиции не восстанавливается). Поэтому мастерство `M_s` считается честно только на 522 верифицированных; 517 висят в `ld-live`.
- **Следствие для радара:** `ld-live` = 656 раздут этими дефолтами; `capture` всего 47. Распределение по темам **неравномерно** — это контентная проблема (см. §7).

## 7. Фаза 2 (реализована) + открытые вопросы

**Фаза 2 — реализована в движке:**
1. **Межсессионный SRS (интервальные повторения по датам).** `recordEpisode` получает `now` (реальное время). Чистое решение растит `rec.srsLevel` по лестнице интервалов **1 → 3 → 7 → 16 → 35 → 75 дней** (`rec.dueDate = now + интервал`); любой промах или подсказка сбрасывает уровень в 0. В `pickNext(profile, pool, domain, now)` задачи с `dueDate ≤ now` — высший приоритет повторов (перед внутрисессионными), лимит те же 3/сессию, «не подряд». Задача возвращается в ДРУГОЙ день.
2. **Поднавыки (доменные оффсеты рейтинга).** `ability(domain) = Auser + domainOffset[domain]`. После rated-эпизода оффсет дрейфует к остаточному отклонению: `domainOffset[D] += 16·(Q_rating − E_domain)`, clamp ±140. Целевая сложность в `pickNext` считается **per-domain** (`Dtarget` от `ability(domain)`), так что сильный в захвате получает захват сложнее, слабый в ld — ld легче. `relativeLabel` и `domainStats` тоже per-domain. Профили `training.v3` forward-compatible (оффсеты/SRS инициализируются пустыми — прогресс не теряется).

**Открытые:**
1. **Неравномерность по навыкам.** После генерации: capture 243, ld-kill 223, ld-live 744, ko 90, race 96, connect 74. connect/race/ko генерацией не берутся (см. `content-generation-findings.md`) — отдельный tactical-shape заход.
2. **Тонкие теги / межсессионный UI** повторов (напоминания «на сегодня N повторов») — фаза 3.
